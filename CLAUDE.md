## Commands

All commands run from the repo root via Bun workspaces (`client`, `server`, `core`, `e2e`).

- `bun install` — install/link dependencies for all workspaces
- `bun run dev` — run client and server dev servers together (`bun run --filter '*' dev`)
- `bun run dev:client` — client only (Vite dev server, default port 5173, falls back to next free port)
- `bun run dev:server` — server only (`bun --watch server/src/index.ts`, port 3001 by default, override with `PORT`)
- `bun run build` — production build of the client (`tsc -b && vite build` in `client/`)
- `bun run typecheck` — typecheck `core` and the server (`tsc --noEmit` in each); the client typechecks as part of its own `build`
- `cd client && bun run lint` — lint the client with oxlint
- `bun run test:e2e` — run Playwright e2e tests (`e2e/`). See the `e2e-test-writer` agent (`.claude/agents/e2e-test-writer.md`) for harness mechanics (separate test database, fixture seeding, rate-limit interaction), and "Testing strategy" below for when e2e is (and isn't) the right tool.
- `bun run test` — run client component tests once (`vitest run` in `client/`). `cd client && bun run test:watch` reruns on change; `cd client && bun run test:ui` opens Vitest's interactive dashboard. See "Component testing" below before writing new specs.
- `bun run test:server` — run server tests (`bun --env-file=.env.test test` in `server/`, Bun's built-in test runner). See "Server testing" below before writing new specs.

## Architecture

This is a Bun workspace monorepo with four packages:

- **`server/`** — Express 5 API. Bun runs the TypeScript source directly (`bun --watch src/index.ts`); there is no compile step for the server, `tsc` is used for type-checking only (`noEmit: true` in `server/tsconfig.json`).
- **`client/`** — React + TypeScript SPA scaffolded with Vite. Data fetching uses `axios` (not the raw `fetch` API) as the HTTP client, wrapped in TanStack Query (`@tanstack/react-query`) `useQuery`/`useMutation` hooks rather than manual `useEffect`/`useState` fetch logic — see `client/src/main.tsx` for the `QueryClientProvider` setup and `client/src/pages/UsersTable.tsx` for the pattern to follow.
- **`core/`** — code shared between `client` and `server`, currently `zod` schemas (see "Data validation" below). Consumed as the plain workspace package `core` (`import { ... } from "core"`), not a `@scope/` name. No compile step, same as `server/`: `package.json`'s `main`/`exports` point straight at `src/index.ts`, and because it's Bun-workspace-linked (a real symlink into `node_modules`, not a copied/published package), both Bun (server) and Vite (client) resolve and transform that TypeScript source directly. `bun run typecheck` covers it via its own `tsc --noEmit`.
- **`e2e/`** — Playwright e2e test harness, isolated from the dev database via a separate `helpdesk_test` Postgres database. Harness mechanics (webServer setup, `.env.test`, fixture seeding, `reuseExistingServer` caveats, rate-limit interaction) live in the `e2e-test-writer` agent (`.claude/agents/e2e-test-writer.md`) rather than here, since they only matter when actually writing/running e2e tests — read that file before touching anything under `e2e/`.

**When writing or updating e2e tests, delegate to the `e2e-test-writer` subagent** (`Agent` tool, `subagent_type: "e2e-test-writer"`) instead of writing Playwright specs directly — it knows the fixture-seeding requirement (the test DB starts empty and public signup is disabled), the shared sign-in rate-limit budget across a run, and the port-reuse footgun with an already-running dev server. Writing specs inline without that context risks flaky or dev-data-corrupting tests. This applies whether the request is to add coverage for a new flow or to update existing specs under `e2e/tests/`.

In development, the client's Vite dev server proxies `/api/*` requests to the server (`client/vite.config.ts` → `http://localhost:3001`), so the client fetches same-origin paths like `/api/health` without CORS configuration.

`server/src/index.ts` wires up the app (CORS, trust proxy, better-auth handoff, session middleware) and exposes `/api/health` and `/api/hello`, which exist to prove the client/server/proxy wiring rather than as feature implementations. Feature endpoints live in their own router modules under `server/src/routes/` (e.g. `users.ts` for `/api/me`, `/api/users`), mounted onto `app` in `index.ts`.

### Data validation

Use `zod` for validating external input — request bodies on the server, form input on the client — rather than hand-rolled `typeof`/regex checks.

**Any schema that validates the same input shape on both sides of the API boundary belongs in `core/`, not duplicated in `client/` and `server/`.** Add it under `core/src/schemas/` (one file per resource, e.g. `user.ts`), export it (plus its inferred `z.infer` type) from `core/src/index.ts`, and import it by name from the `core` package in both workspaces — see `createUserSchema/CreateUserInput` in `core/src/schemas/user.ts` for the pattern. A schema that's genuinely local to one side (e.g. a server-only internal query-param schema with no client form behind it) can still live next to its own route/component instead.

- **Server**: validate with `.safeParse(req.body)` using the imported schema, returning the first issue's message as a `400`. See the `POST /api/users` handler in `server/src/routes/users.ts`, which imports `createUserSchema` from `core`.
- **Client**: pair the imported schema with `react-hook-form` via `@hookform/resolvers/zod`'s `zodResolver`, rather than validating in the submit handler by hand — `register()` each field, read errors off `formState.errors`, and type the form with the schema's inferred type (e.g. `CreateUserInput`) instead of redeclaring it. `client/src/pages/UserForm.tsx` is the reference example; `LoginPage.tsx` predates this convention and still defines its schema locally. `register()` only works for native inputs — a non-native field bound to the same form state, like the `role` `Select`, needs `Controller` instead (`<Controller control={control} name="role" render={({ field }) => <Select value={field.value} onValueChange={field.onChange}>...} />`).

`UserForm.tsx` also illustrates the form/chrome split to follow for anything presented in a modal: the form component owns `useForm`, the `zod` schema, and the submit mutation, and reports out via an `onSuccess` callback prop rather than reaching into the dialog's open state directly. `CreateUserDialog.tsx` and `EditUserDialog.tsx` are just the `Dialog` trigger/header wrapping it, passing `onSuccess={() => setOpen(false)}` — each relies on Radix's `Dialog.Content` unmounting on close (no `forceMount`) to discard the form's local state, rather than an explicit `reset()`. This keeps the form reusable outside a dialog and independently testable (`UserForm.test.tsx` covers validation/submission; the dialog test files only cover open/close wiring).

`UserForm` itself takes a discriminated-union `mode` prop (`"create" | "edit"`) rather than being two near-duplicate components: `mode: "edit"` additionally takes `userId` and `defaultValues`, submits with `axios.patch` instead of `axios.post`, and validates against `core`'s `updateUserSchema` (same shape as `createUserSchema`, but the password field also accepts `""` to mean "leave unchanged" — the server mirrors this by only touching the credential `Account` row when `password` is non-empty). Follow this pattern — a `mode` union on one form component — for any other resource that gets both a create and an edit dialog, instead of forking the form.

The same split applies one level up, between a route-level page and the data-fetching component(s) it composes: `UsersPage.tsx` is layout only (heading, `CreateUserDialog`, `UsersTable`), while `UsersTable.tsx` owns the `useQuery` call and all of its loading/error/empty/populated states. Prefer this over folding fetching and every state branch directly into the page component — it keeps the page trivial to read and lets the data component be tested (and reused) independently of page layout.

`EditUserDialog.tsx` and `DeleteUserDialog.tsx` show the pattern for a dialog that a *list* triggers per-row: don't render one dialog instance per row (`open` state duplicated N times). Instead the list (`UsersTable.tsx`) holds one piece of state per dialog type — `editingUser` / `deletingUser`, each `T | null` — and renders exactly one `<EditUserDialog>` / `<DeleteUserDialog>` after the table, controlled (`user`, `onOpenChange`) rather than owning its own `open` state or trigger. Each row's button just calls `setEditingUser(user)` / `setDeletingUser(user)`; the dialog is `open={user !== null}`. `null`-vs-`T` is the only state needed — don't reintroduce a separate boolean alongside it.

### Core enums (`Role`, `TicketStatus`, `TicketCategory`)

**Never write these values as literal strings — import the enum from `core` and use it, in both `client/` and `server/`, for every use: value comparisons *and* type annotations.** `user.role === Role.ADMIN`, not `user.role === "ADMIN"`. `<SelectItem value={Role.AGENT}>`, not `value="AGENT"`. And just as much for typing a field: `status: TicketStatus` on a local type (e.g. `TicketListItem` in `TicketsTable.tsx`), not `status: "OPEN" | "RESOLVED" | "CLOSED"` spelled out inline — even though the two are structurally identical to the type checker, naming the shared enum type keeps one source of truth and makes the field's connection to it explicit at a glance, and it's the pattern every list-item type in this codebase already follows (`role: Role` in `UsersTable.tsx`'s `UserListItem`, `status`/`category` in `TicketsTable.tsx`'s `TicketListItem`).

Each is a plain `const` object, not TypeScript's `enum` keyword — deliberately, matching how Prisma itself generates them in `server/src/generated/prisma/enums.ts` (Prisma stopped emitting real `enum`s; they aren't erasable/isolated-modules-safe, which matters here since both Bun and Vite transpile file-by-file). Keeping `core`'s copy the same shape as Prisma's, rather than using `enum`, means the two stay structurally interchangeable with no casts — a real TS `enum` would be a *nominal* type and wouldn't be. `core` still can't import the Prisma-generated ones directly (`client` must never pull in server-only generated code), so each value set is declared twice by necessity (`core/src/schemas/user.ts`'s `Role`, `core/src/schemas/ticket.ts`'s `TicketStatus`/`TicketCategory`) — keep both copies in sync if the values ever change.

**On the client, `core`'s copy is the only option — always import from there.** On the server, prefer Prisma's own generated enum (`server/src/generated/prisma/enums.ts`) directly instead: the server already has native access to it, so routing through `core`'s client-safe re-declaration there is pointless indirection, not "using the shared source." `server/src/lib/auth.ts`'s `Role` and `server/src/routes/tickets.ts`'s `TicketStatus`/`TicketCategory` both do this. The one place `core`'s copy is legitimately needed server-side is inside a shared `core` schema itself (e.g. `createUserSchema`'s `z.nativeEnum(Role, ...)` in `core/src/schemas/user.ts`) — that file has to use its own `Role`, since the schema is what the client validates against too.

### Soft deletion

`User` rows are soft-deleted (`deletedAt: DateTime?` in `schema.prisma`), never hard-deleted — `DELETE /api/users/:id` sets `deletedAt`, it doesn't run `prisma.user.delete`. Follow this for any other resource that needs "delete": add a nullable `deletedAt` column via a migration, filter it out of list/lookup queries (`where: { deletedAt: null }`, as in `GET /api/users`), and never actually remove the row.

Two things a soft-deleted `User` specifically needs, beyond the column itself:
- **It must stop being a valid session.** `deletedAt` is declared as a `user.additionalFields` entry in `server/src/lib/auth.ts` (`input: false`, so it's never settable through better-auth's public API) purely so it comes back on every `auth.api.getSession()` call; `server/src/middleware/session.ts` then treats a session whose user has `deletedAt` set as if there were no session at all (`req.user`/`req.session` both `null`), rather than only hiding the user from list views. A soft delete that leaves existing sessions live isn't really a delete.
- **Business rules on who can be deleted belong in the route handler, not the schema** — `DELETE /api/users/:id` 403s when `existing.role === "ADMIN"`, checked against the target row fetched fresh from the DB, not the caller's own role.

For confirming a destructive action, use shadcn's `alert-dialog.tsx` (`role="alertdialog"`, not `dialog.tsx`'s `role="dialog"`) rather than the plain `Dialog` — see `DeleteUserDialog.tsx`. One non-obvious bit of its wiring: `AlertDialogAction` is a `Dialog.Close` under the hood, so a plain `onClick` still closes the dialog immediately regardless of whether your mutation succeeds. Call `event.preventDefault()` in the action's `onClick` and close manually (via the `onOpenChange` prop passed down, same as `EditUserDialog`) only from the mutation's `onSuccess` — otherwise a failed delete silently closes the confirmation instead of showing the error.

### Error handling

Express 5 automatically forwards a rejected promise from an `async` route handler to the error-handling middleware — unlike Express 4, you don't need to wrap the handler body in `try/catch` (or a `catchAsync`-style helper) just to keep the process from crashing on an unhandled rejection. The handlers in `server/src/routes/users.ts` (`POST /api/users`, `GET /api/users`) let Prisma/zod errors propagate this way.

Only reach for `try/catch` when you need to turn a specific failure into a specific response, rather than the default error handling. `GET /api/health` is the example: it catches so it can report `503 { status: "error", database: "unreachable" }` instead of a generic 500, since the probe's whole purpose is distinguishing "DB unreachable" from "server down."

### Rate limiting

Two layers, both IP-keyed:

- **`/api/auth/*`** (sign-in, sign-up, session, etc.): better-auth's built-in limiter (`server/src/lib/auth.ts`), forced on in all environments (`enabled: true`) rather than its "production only" default, so dev/test behavior matches prod. Sign-in/sign-up/password-change get a stricter built-in 3-requests/10s rule automatically; everything else under `/api/auth` gets the configured 100/60s default. Counters are stored in Postgres (`rate_limit` table, added by the `add_rate_limit_table` migration) rather than in-memory, so counts stay correct across multiple server instances — no Redis dependency needed just for this.
- **Everything else** (`/api/hello`, `/api/me`, `/api/users`): `express-rate-limit`, 100 requests/60s, in-memory. The limiter (`apiLimiter`) is defined once in `server/src/middleware/rate-limit.ts` and applied per-route in `server/src/index.ts` (`/api/hello`) and `server/src/routes/users.ts` (`/api/me`, `/api/users`). `/api/health` is deliberately excluded — it's an infra health probe (ALB target group) and must not be throttled.

Both need the real client IP to key correctly, which only works if two things are set per environment:

- **`NODE_ENV`** — must be `development`/`test`/`production` (set in `server/.env`, `server/.env.test`, and the production task definition respectively). Without it, better-auth's own IP resolution can't identify local requests and every client collapses into one shared bucket per path — a real correctness bug, not just a missing nicety.
- **`TRUSTED_PROXY_CIDRS`** — comma-separated CIDR list of trusted proxies, read by both `app.set("trust proxy", ...)` in `index.ts` and better-auth's `advanced.ipAddress.trustedProxies` in `auth.ts`. Empty in dev/test (no proxy in front locally). In production, set it to the VPC CIDR the ALB forwards from (see `tech-stack.md`'s deployment section) — without it, `X-Forwarded-For` isn't trusted and every request behind the ALB looks like it comes from the same place.

### Testing strategy: component tests first, e2e only when necessary

**Default to a component test — client (Vitest + RTL) or server (`bun:test` + `supertest`, see "Server testing" below) — and reach for `e2e/` only when the behavior genuinely can't be verified without a real browser.** Most of what needs covering fits the former: a component's loading/error/empty/populated states, form validation, a route's auth/validation/response-shape logic. It's not just style — component/server tests run in milliseconds to a few hundred ms with everything mocked or hit directly, where the e2e suite needs a live Postgres, two dev servers, and an actual browser, and takes 10+ seconds per run.

Reach for `e2e/` when a component test structurally can't cover it: real page navigation and client-side routing, a redirect, a cookie/session persisting across a reload, or a flow that genuinely spans client and server together in a way a mocked-`axios` component test can't represent. When a new test is needed, default to writing it as a component/server test first; add an e2e spec only for the specific slice of behavior that requires a browser, not the whole flow.

This is also why `server/src/routes/tickets.test.ts` replaced the original `e2e/tests/ticket-ingestion.spec.ts` for `POST /api/tickets`: that endpoint's behavior (secret-header check, zod validation, response shape) is pure request/response logic with no browser involved, so it moved to a server test once that harness existed.

### Component testing

Client component tests use Vitest + React Testing Library, jsdom environment. Config lives in `client/vite.config.ts`'s `test` block (`/// <reference types="vitest/config" />` at the top of that file makes the `test` key available on `defineConfig` from `vite`); global setup is `client/src/test/setup.ts` (registers `@testing-library/jest-dom/vitest` matchers and calls RTL's `cleanup()` in `afterEach` — required because the config doesn't set `globals: true`, so every test file imports `describe`/`it`/`expect`/etc. from `vitest` explicitly rather than relying on ambient globals).

When writing a new spec:

- **Location & naming**: colocate as `Component.test.tsx` next to the component it tests (e.g. `client/src/pages/UsersPage.tsx` → `client/src/pages/UsersPage.test.tsx`), not in a separate `__tests__` tree.
- **Data fetching**: don't hit the real API. `vi.mock("axios")` at the top of the file, then `vi.mocked(axios, true)` to get a typed mock and set per-test behavior with `mockResolvedValue`/`mockRejectedValue`/`mockReturnValue` (reset in `beforeEach` so tests don't leak mock state into each other).
- **TanStack Query components**: any component using `useQuery`/`useMutation` needs a `QueryClientProvider` ancestor in the test render — use the `renderWithQuery` helper from `client/src/test/render-with-query.tsx` instead of hand-rolling a `QueryClient` per test file. It wires up a fresh client per render with `retry: false` (so a mocked rejection surfaces immediately instead of retrying and timing out the test).
- **Async assertions**: query pending/loaded/error states with RTL's `findBy*`/`findAllBy*` (they wait), not `getBy*` immediately after a fetch-triggering render.
- **Ambiguous text matches**: shadcn components often duplicate visible text (e.g. a table column header and a badge in that column can both say "Verified") — disambiguate with `getByText(text, { selector: "span" })` or scope with `within(row)` rather than reaching for `getAllByText` and indexing blindly.
- **Radix `Select`**: jsdom doesn't implement `hasPointerCapture`/`setPointerCapture`/`releasePointerCapture`/`scrollIntoView`, which Radix's `Select` calls on open — `client/src/test/setup.ts` stubs all four globally, so you shouldn't need to touch that again. To actually pick a value in a test, drive the real interaction (`fireEvent.click` the trigger via `getByLabelText`, then `fireEvent.click` the option via `findByRole("option", { name })`) rather than `fireEvent.change` — it isn't a native input. See `selectRole` in `client/src/pages/UserForm.test.tsx`.

`client/src/pages/UsersTable.test.tsx` is the reference example for all of the above (loading-skeleton state, populated table, empty state, error state).

### Server testing

Server tests use Bun's built-in test runner (`bun:test` — `describe`/`test`/`expect`, Jest-compatible matchers including `toMatchObject`) plus `supertest` against the Express `app` directly, **not** Playwright/the e2e harness — per "Testing strategy" above, this is where a route's auth/validation/response-shape logic belongs.

- **The app must be importable without binding a port**: `server/src/app.ts` exports the fully configured `app` (all middleware/routes); `server/src/index.ts` is a thin two-line entry point that imports it and calls `app.listen(...)`. Tests import `app` from `app.ts` and drive it with `supertest(app)` — never import `index.ts`, which would bind a real port as a side effect.
- **Database**: tests run against the same `helpdesk_test` database the e2e suite uses (`bun --env-file=.env.test test`, per `server/package.json`'s `test` script — this is what loads `EMAIL_INGEST_SECRET`, `DATABASE_URL`, etc. from `.env.test`), not a mocked Prisma client. Unlike the e2e database, don't let rows accumulate: track anything a test creates and delete it in `afterAll` (see `createdTicketIds` in `routes/tickets.test.ts`).
- **Location & naming**: colocate as `Route.test.ts` next to the route file it tests (e.g. `server/src/routes/tickets.ts` → `server/src/routes/tickets.test.ts`), mirroring the client's colocation convention.

`server/src/routes/tickets.test.ts` is the reference example (auth-header checks, zod validation, response shape, and the cleanup pattern above).

### Tickets: deliberately minimal, email ingestion still unresolved

`Ticket` (`schema.prisma`) exists but only as much as `project-scope.md`'s *settled* decisions require: `id` is a numeric autoincrement (not the string/UUID `id` pattern every other model in this schema uses), `status` (`OPEN`/`RESOLVED`/`CLOSED`, per the ticket-statuses decision), an optional `category` (`TicketCategory`: `GENERAL_QUESTION`/`TECHNICAL_QUESTION`/`REFUND_REQUEST`, per the categories decision) with **no default** — it's `null`/unset until AI classification actually runs, not defaulted to a guess, since nothing populates it yet (that's a later implementation-plan phase). No Message-ID/threading fields — reply-threading strategy is still an open question, unlike ticket categories which are already decided. Don't add ingestion/threading fields without a decision recorded in `project-scope.md` first, per the rule above.

**`POST /api/tickets`** (`server/src/routes/tickets.ts`) is how a ticket gets created from an email today: it accepts `{ from, subject?, body }` and inserts a `Ticket`. It does **not** talk to a real mailbox — `project-scope.md`'s "Email ingestion" open question (Gmail API vs. Microsoft Graph vs. generic IMAP vs. an inbound-parse webhook provider) is still unresolved, so this endpoint is the provider-agnostic landing point a real integration will call into once that's decided, not the integration itself.

Because the real caller here is a webhook (an email provider's server), not a signed-in browser, this route is gated by a shared secret (`EMAIL_INGEST_SECRET` env var, checked against the `x-ingest-secret` request header) instead of `req.user`/session auth like every other mutating route in this codebase. Follow that same pattern — not session auth — for any other endpoint whose real caller is a system, not a person: check the header against the env var and **fail closed if the env var itself is unset** (`if (!expectedSecret || header !== expectedSecret)`, not just `header !== expectedSecret` — the latter silently passes when both sides are `undefined`).

**`GET /api/tickets`** is the one exception to "gate reads/writes to ADMIN" that every `users.ts` route follows: it only requires `req.user` to exist, no role check, per `project-scope.md`'s "Agent permissions" decision (regular agents have full ticket control, not just admins). `/tickets` (`TicketsPage.tsx`/`TicketsTable.tsx`, following the same page/data-component split as `UsersPage.tsx`/`UsersTable.tsx`) is routed under `ProtectedRoute` in `App.tsx`, not `AdminRoute` like `/users` — same reasoning. `TicketStatus`/`TicketCategory` are exported from `core` (`core/src/schemas/ticket.ts`) as the same const-object "enum" pattern as `Role`, for the same reason: `client` needs magic-string-free values for badge rendering, and `core` can't depend on Prisma's generated output.

**Sorting, filtering, and pagination are all server-side** — `TicketsTable.tsx` renders whatever `GET /api/tickets` returns rather than sorting/filtering/paginating the fetched page itself. This is why the endpoint returns `{ tickets, total, page, pageSize }` rather than just `tickets`: `total` is the full (filtered) count across all pages, needed to compute how many pages exist, since the client only ever holds one page's worth of rows.

- **Sorting**: via TanStack Table in `manualSorting` mode. `useReactTable`'s `SortingState` (one column, `enableMultiSort: false`/`enableSortingRemoval: false` so it's always exactly `[{ id, desc }]`, never empty or multi-column) drives the `useQuery`'s `sortBy`/`sortOrder` params directly — clicking a column header changes `sorting`, which changes the query key, which triggers a refetch with the new params. The endpoint validates `sortBy` against an explicit allow-list of real `Ticket` columns (`id`/`subject`/`requesterEmail`/`status`/`category`/`createdAt`) before it ever reaches `prisma.ticket.findMany`'s `orderBy` — it's a real HTTP query param any caller can set, so an un-validated value would let an arbitrary/invalid field name through to Prisma.
- **Filtering**: plain `Select` dropdowns (status, category) above the table, each backed by its own `useState`, also included in the `useQuery` key/params. An `"ALL"` sentinel means "no filter" (omit the param entirely) rather than sending an empty string — Radix's `Select.Item` can't take `""` as a value, since that's reserved for "nothing selected." A second sentinel, `"UNCLASSIFIED"`, means "`category` is `null`" — a query param can't express `null` any other way, so the server (`server/src/routes/tickets.ts`) special-cases that exact string to `{ category: null }` in the Prisma `where`, and it's a real `z.literal("UNCLASSIFIED")` in the validation schema alongside `z.nativeEnum(TicketCategory)`, not an unchecked passthrough.
- **Date-range filtering**: two native `<input type="date">` elements (`createdFrom`/`createdTo`, each its own `useState<string>`, `""` for unset) alongside the `Select` filters, same pattern — included in the `useQuery` key, omitted from `params` entirely when empty rather than sent as `""`. The wire format is the input's own native value, plain `"YYYY-MM-DD"`; no client-side `Date` parsing needed since the string round-trips straight to the query param. Server-side, `z.coerce.date()` parses that string as UTC midnight, so `createdFrom` (used as `gte`) is naturally inclusive of its whole day, but `createdTo` used bare as `lte` would only include that day's first instant — the route expands it to `23:59:59.999` UTC (an `endOfDay` helper) before building the Prisma `where`, so the end date is inclusive too. A `.refine` on the query schema 400s if `createdFrom` is after `createdTo`, rather than silently returning an empty result set for a swapped range.
- **Pagination**: TanStack Table in `manualPagination` mode — `PaginationState` (`pageIndex`, 0-indexed; `pageSize`, default 10) drives `page`/`pageSize` query params (`page` is 1-indexed over the wire — the `+ 1`/`- 1` conversion happens at the query-building boundary, not in state). `pageCount` is computed from the response's `total` (`Math.ceil(total / pageSize)`) and passed back into `useReactTable` so `table.getCanNextPage()`/`getCanPreviousPage()` work correctly. `pageSize` is capped server-side at 100 (`z.coerce.number().max(100)`) so a caller can't force-load the whole table in one request. **Changing sort or a filter resets `pageIndex` to 0** — otherwise the user can get stranded on a page number that doesn't exist for the new result set.

Follow this same shape (`ColumnDef` column ids / filter values matching a server-side allow-list, `manualSorting`/`manualPagination: true`, sort+filter+pagination state all in the query key, reset to page 1 on sort/filter change) for any other list that needs sortable/filterable/paginated columns — don't reach for TanStack Table's built-in client-side sorting/filtering/pagination (`getSortedRowModel`/`getFilteredRowModel`/`getPaginationRowModel`) for data that shouldn't be fully loaded client-side just to slice, sort, or filter it.

**Ticket detail page**: `TicketsTable.tsx`'s subject cell is a `react-router-dom` `Link` to `/tickets/:id` (`TicketDetailPage.tsx`, routed in `App.tsx` under `ProtectedRoute` alongside `/tickets`), which fetches the single ticket via `GET /api/tickets/:id` (`server/src/routes/tickets.ts`) — same `req.user`-only access rule as the list endpoint, no role check. The list endpoint's `TicketListItem` (`TicketsTable.tsx`) intentionally omits `body`/`updatedAt`, since a paginated list response shouldn't carry a field only the single-ticket view needs; the full shape (`Ticket`, including `body`) plus the `categoryLabels`/`statusBadgeVariant` display maps live in `client/src/lib/ticket-display.ts` so the list and detail views can't render a status/category differently. `:id` is validated with `z.coerce.number().int().positive()` against the route param (400 if it isn't numeric — `Ticket.id` is a numeric autoincrement, unlike `User.id`) before the `prisma.ticket.findUnique` lookup, which 404s if nothing matches.

Testing this needed `client/src/test/render-with-query.tsx` (the shared `renderWithQuery` test helper) to also wrap renders in a `MemoryRouter` — any component reaching for `Link` (now including `TicketsTable.tsx`) throws without a `Router` ancestor. A component that reads route state itself, like `TicketDetailPage.tsx`'s `useParams`, needs the `ui` passed to `renderWithQuery` wrapped in its own `<Routes><Route path="/tickets/:id" element={...} /></Routes>`, with the target path passed via the helper's `initialEntries` option — see `TicketDetailPage.test.tsx`.

**Ticket assignment**: `Ticket.assignedToId` (nullable, `onDelete: SetNull`) is a plain FK to `User` — `assignedTo` (`{ id, name, email }`, via `include` on both `GET /api/tickets` and `GET /api/tickets/:id`) is the populated shape both the list's Assignee column and the detail page's picker render. `PATCH /api/tickets/:id/assign` (body `{ assignedToId: string | null }`, `null` unassigns) does the reassignment; per `project-scope.md`'s "Agent permissions" decision this is `req.user`-only like every other ticket endpoint, not ADMIN-gated — any authenticated user can reassign any ticket. It 404s if the ticket doesn't exist, and separately 404s (`"Assignee not found"`) if `assignedToId` is set but doesn't resolve to a non-soft-deleted `User`.

`assignedToId` validation is two-layered, both required: the zod schema (`z.string().min(1).nullable()`) rejects `""` outright rather than accepting any string, and the handler checks existence with `assignedToId !== null` rather than a truthy check — a truthy check would let an empty string (if it ever got past the schema some other way) skip the `prisma.user.findUnique` lookup and hit `prisma.ticket.update` directly, where a nonexistent id fails as an opaque FK-constraint 500 instead of the clean `404 "Assignee not found"` every other invalid-assignee case returns. Follow this same two-layer shape (schema rejects the empty/degenerate value, handler existence-checks with the real "did the caller mean to omit this" condition rather than JS truthiness) for any other nullable-FK-by-id body field.

**Updating status/category**: `PATCH /api/tickets/:id` (distinct from `PATCH /api/tickets/:id/assign` — a general ticket update vs. the assignment relation specifically) takes `{ status?, category? }`, both independently optional so a caller can change either field alone or both together in one request; `updateTicketSchema`'s `.refine` 400s if neither is present, rather than silently no-opping. `category` is nullable *and* optional — omitted means "leave it," explicit `null` means "clear it back to unclassified" (overriding an AI classification, per `project-scope.md`'s "Agent permissions" decision), `status` has no such unset state since a ticket always has one. Same access rule as every other ticket endpoint: `req.user`-only, not ADMIN-gated. On the client, `TicketDetailPage.tsx`'s Status and Category are `Select`s (not the read-only `Badge`/text `TicketsTable.tsx` still uses in its list columns) sharing one `updateTicket` mutation — each `onValueChange` calls `updateTicket.mutate({ status })` or `updateTicket.mutate({ category })` with only its own field, matching the endpoint's partial-update semantics; `"UNCLASSIFIED"` is the same kind of client-only sentinel as `TicketsTable.tsx`'s filter and the assignee picker's `"UNASSIGNED"`, mapped to `null` before the request goes out.

Populating the "assign to" picker needed a users endpoint any authenticated user (not just admins) can call, so `GET /api/users/assignable` (`server/src/routes/users.ts`) exists alongside the ADMIN-only `GET /api/users` — deliberately minimal (`id`/`name`/`email` only, no `role`/`emailVerified`/`createdAt`) rather than reusing the admin list's shape with looser permissions. Follow this same split — a separate, minimally-shaped, non-admin-gated endpoint — for any other case where a non-admin flow needs to reference "a user" without needing the full admin user-management view.

`TicketDetailPage.tsx`'s assignee `Select` is a direct-mutate control, not a form: `onValueChange` calls `assignTicket.mutate(...)` straight away (no submit button), same as `TicketsTable.tsx`'s filter `Select`s triggering a requery on change. `"UNASSIGNED"` is the sentinel for "no assignee" (same reasoning as `TicketsTable.tsx`'s `ALL`/`UNCLASSIFIED` — Radix's `Select.Item` can't use `""`). On success it invalidates both `["ticket", id]` and, via TanStack Query's key-prefix matching, every `["tickets", ...]` list query, so the Assignee column stays in sync if the user navigates back without an explicit refetch call. Asserting a mutation's request body in a test needs `await waitFor(...)`, not a synchronous `expect` right after the triggering `fireEvent` — `mutate()` (unlike an inline-`await`ed `mutateAsync`) doesn't run its `mutationFn` before the next line executes; see `TicketDetailPage.test.tsx`'s assignment tests and the pre-existing pattern in `EditUserDialog.test.tsx`.

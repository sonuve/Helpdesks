## Commands

All commands run from the repo root via Bun workspaces (`client`, `server`, `core`, `e2e`).

- `bun install` — install/link dependencies for all workspaces
- `bun run dev` — run client and server dev servers together (`bun run --filter '*' dev`)
- `bun run dev:client` — client only (Vite dev server, default port 5173, falls back to next free port)
- `bun run dev:server` — server only (`bun --watch server/src/index.ts`, port 3001 by default, override with `PORT`)
- `bun run build` — production build of the client (`tsc -b && vite build` in `client/`)
- `bun run typecheck` — typecheck `core` and the server (`tsc --noEmit` in each); the client typechecks as part of its own `build`
- `cd client && bun run lint` — lint the client with oxlint
- `bun run test:e2e` — run Playwright e2e tests (`e2e/`). See the `e2e-test-writer` agent (`.claude/agents/e2e-test-writer.md`) for harness mechanics (separate test database, fixture seeding, rate-limit interaction), and "Testing strategy" below for when e2e is (and isn't) the right tool.
- `bun run test` — run client component tests once (`vitest run` in `client/`). `cd client && bun run test:watch` reruns on change; `cd client && bun run test:ui` opens Vitest's interactive dashboard. See "Component testing" below before writing new specs.
- `bun run test:server` — run server tests (`bun --env-file=.env.test test` in `server/`, Bun's built-in test runner). See "Server testing" below before writing new specs.

## Architecture

This is a Bun workspace monorepo with four packages:

- **`server/`** — Express 5 API. Bun runs the TypeScript source directly (`bun --watch src/index.ts`); there is no compile step for the server, `tsc` is used for type-checking only (`noEmit: true` in `server/tsconfig.json`).
- **`client/`** — React + TypeScript SPA scaffolded with Vite. Data fetching uses `axios` (not the raw `fetch` API) as the HTTP client, wrapped in TanStack Query (`@tanstack/react-query`) `useQuery`/`useMutation` hooks rather than manual `useEffect`/`useState` fetch logic — see `client/src/main.tsx` for the `QueryClientProvider` setup and `client/src/pages/UsersTable.tsx` for the pattern to follow.
- **`core/`** — code shared between `client` and `server`, currently `zod` schemas (see "Data validation" below). Consumed as the plain workspace package `core` (`import { ... } from "core"`), not a `@scope/` name. No compile step, same as `server/`: `package.json`'s `main`/`exports` point straight at `src/index.ts`, and because it's Bun-workspace-linked (a real symlink into `node_modules`, not a copied/published package), both Bun (server) and Vite (client) resolve and transform that TypeScript source directly. `bun run typecheck` covers it via its own `tsc --noEmit`.
- **`e2e/`** — Playwright e2e test harness, isolated from the dev database via a separate `helpdesk_test` Postgres database. Harness mechanics (webServer setup, `.env.test`, fixture seeding, `reuseExistingServer` caveats, rate-limit interaction) live in the `e2e-test-writer` agent (`.claude/agents/e2e-test-writer.md`) rather than here, since they only matter when actually writing/running e2e tests — read that file before touching anything under `e2e/`.

**When writing or updating e2e tests, delegate to the `e2e-test-writer` subagent** (`Agent` tool, `subagent_type: "e2e-test-writer"`) instead of writing Playwright specs directly — it knows the fixture-seeding requirement (the test DB starts empty and public signup is disabled), the shared sign-in rate-limit budget across a run, and the port-reuse footgun with an already-running dev server. Writing specs inline without that context risks flaky or dev-data-corrupting tests. This applies whether the request is to add coverage for a new flow or to update existing specs under `e2e/tests/`.

In development, the client's Vite dev server proxies `/api/*` requests to the server (`client/vite.config.ts` → `http://localhost:3001`), so the client fetches same-origin paths like `/api/health` without CORS configuration.

`server/src/index.ts` wires up the app (CORS, trust proxy, better-auth handoff, session middleware) and exposes `/api/health` and `/api/hello`, which exist to prove the client/server/proxy wiring rather than as feature implementations. Feature endpoints live in their own router modules under `server/src/routes/` (e.g. `users.ts` for `/api/me`, `/api/users`), mounted onto `app` in `index.ts`.

### Data validation

Use `zod` for validating external input — request bodies on the server, form input on the client — rather than hand-rolled `typeof`/regex checks.

**Any schema that validates the same input shape on both sides of the API boundary belongs in `core/`, not duplicated in `client/` and `server/`.** Add it under `core/src/schemas/` (one file per resource, e.g. `user.ts`), export it (plus its inferred `z.infer` type) from `core/src/index.ts`, and import it by name from the `core` package in both workspaces — see `createUserSchema/CreateUserInput` in `core/src/schemas/user.ts` for the pattern. A schema that's genuinely local to one side (e.g. a server-only internal query-param schema with no client form behind it) can still live next to its own route/component instead.

- **Server**: validate with `.safeParse(req.body)` using the imported schema, returning the first issue's message as a `400`. See the `POST /api/users` handler in `server/src/routes/users.ts`, which imports `createUserSchema` from `core`.
- **Client**: pair the imported schema with `react-hook-form` via `@hookform/resolvers/zod`'s `zodResolver`, rather than validating in the submit handler by hand — `register()` each field, read errors off `formState.errors`, and type the form with the schema's inferred type (e.g. `CreateUserInput`) instead of redeclaring it. `client/src/pages/UserForm.tsx` is the reference example; `LoginPage.tsx` predates this convention and still defines its schema locally. `register()` only works for native inputs — a non-native field bound to the same form state, like the `role` `Select`, needs `Controller` instead (`<Controller control={control} name="role" render={({ field }) => <Select value={field.value} onValueChange={field.onChange}>...} />`).

`UserForm.tsx` also illustrates the form/chrome split to follow for anything presented in a modal: the form component owns `useForm`, the `zod` schema, and the submit mutation, and reports out via an `onSuccess` callback prop rather than reaching into the dialog's open state directly. `CreateUserDialog.tsx` and `EditUserDialog.tsx` are just the `Dialog` trigger/header wrapping it, passing `onSuccess={() => setOpen(false)}` — each relies on Radix's `Dialog.Content` unmounting on close (no `forceMount`) to discard the form's local state, rather than an explicit `reset()`. This keeps the form reusable outside a dialog and independently testable (`UserForm.test.tsx` covers validation/submission; the dialog test files only cover open/close wiring).

`UserForm` itself takes a discriminated-union `mode` prop (`"create" | "edit"`) rather than being two near-duplicate components: `mode: "edit"` additionally takes `userId` and `defaultValues`, submits with `axios.patch` instead of `axios.post`, and validates against `core`'s `updateUserSchema` (same shape as `createUserSchema`, but the password field also accepts `""` to mean "leave unchanged" — the server mirrors this by only touching the credential `Account` row when `password` is non-empty). Follow this pattern — a `mode` union on one form component — for any other resource that gets both a create and an edit dialog, instead of forking the form.

The same split applies one level up, between a route-level page and the data-fetching component(s) it composes: `UsersPage.tsx` is layout only (heading, `CreateUserDialog`, `UsersTable`), while `UsersTable.tsx` owns the `useQuery` call and all of its loading/error/empty/populated states. Prefer this over folding fetching and every state branch directly into the page component — it keeps the page trivial to read and lets the data component be tested (and reused) independently of page layout.

`EditUserDialog.tsx` and `DeleteUserDialog.tsx` show the pattern for a dialog that a *list* triggers per-row: don't render one dialog instance per row (`open` state duplicated N times). Instead the list (`UsersTable.tsx`) holds one piece of state per dialog type — `editingUser` / `deletingUser`, each `T | null` — and renders exactly one `<EditUserDialog>` / `<DeleteUserDialog>` after the table, controlled (`user`, `onOpenChange`) rather than owning its own `open` state or trigger. Each row's button just calls `setEditingUser(user)` / `setDeletingUser(user)`; the dialog is `open={user !== null}`. `null`-vs-`T` is the only state needed — don't reintroduce a separate boolean alongside it.

### Core enums (`Role`, `TicketStatus`, `TicketCategory`)

**Never write these values as literal strings — import the enum from `core` and use it, in both `client/` and `server/`, for every use: value comparisons *and* type annotations.** `user.role === Role.ADMIN`, not `user.role === "ADMIN"`. `<SelectItem value={Role.AGENT}>`, not `value="AGENT"`. And just as much for typing a field: `status: TicketStatus` on a local type (e.g. `TicketListItem` in `TicketsTable.tsx`), not `status: "OPEN" | "RESOLVED" | "CLOSED"` spelled out inline — even though the two are structurally identical to the type checker, naming the shared enum type keeps one source of truth and makes the field's connection to it explicit at a glance, and it's the pattern every list-item type in this codebase already follows (`role: Role` in `UsersTable.tsx`'s `UserListItem`, `status`/`category` in `TicketsTable.tsx`'s `TicketListItem`).

Each is a plain `const` object, not TypeScript's `enum` keyword — deliberately, matching how Prisma itself generates them in `server/src/generated/prisma/enums.ts` (Prisma stopped emitting real `enum`s; they aren't erasable/isolated-modules-safe, which matters here since both Bun and Vite transpile file-by-file). Keeping `core`'s copy the same shape as Prisma's, rather than using `enum`, means the two stay structurally interchangeable with no casts — a real TS `enum` would be a *nominal* type and wouldn't be. `core` still can't import the Prisma-generated ones directly (`client` must never pull in server-only generated code), so each value set is declared twice by necessity (`core/src/schemas/user.ts`'s `Role`, `core/src/schemas/ticket.ts`'s `TicketStatus`/`TicketCategory`) — keep both copies in sync if the values ever change.

**On the client, `core`'s copy is the only option — always import from there.** On the server, prefer Prisma's own generated enum (`server/src/generated/prisma/enums.ts`) directly instead: the server already has native access to it, so routing through `core`'s client-safe re-declaration there is pointless indirection, not "using the shared source." `server/src/lib/auth.ts`'s `Role` and `server/src/routes/tickets.ts`'s `TicketStatus`/`TicketCategory` both do this. The one place `core`'s copy is legitimately needed server-side is inside a shared `core` schema itself (e.g. `createUserSchema`'s `z.nativeEnum(Role, ...)` in `core/src/schemas/user.ts`) — that file has to use its own `Role`, since the schema is what the client validates against too.

### Soft deletion

`User` rows are soft-deleted (`deletedAt: DateTime?` in `schema.prisma`), never hard-deleted — `DELETE /api/users/:id` sets `deletedAt`, it doesn't run `prisma.user.delete`. Follow this for any other resource that needs "delete": add a nullable `deletedAt` column via a migration, filter it out of list/lookup queries (`where: { deletedAt: null }`, as in `GET /api/users`), and never actually remove the row.

Three things a soft-deleted `User` specifically needs, beyond the column itself:
- **It must stop being a valid session.** `deletedAt` is declared as a `user.additionalFields` entry in `server/src/lib/auth.ts` (`input: false`, so it's never settable through better-auth's public API) purely so it comes back on every `auth.api.getSession()` call; `server/src/middleware/session.ts` then treats a session whose user has `deletedAt` set as if there were no session at all (`req.user`/`req.session` both `null`), rather than only hiding the user from list views. A soft delete that leaves existing sessions live isn't really a delete.
- **Business rules on who can be deleted belong in the route handler, not the schema** — `DELETE /api/users/:id` 403s when `existing.role === "ADMIN"`, checked against the target row fetched fresh from the DB, not the caller's own role.
- **Anything referencing it by FK with `onDelete: SetNull` needs that unassignment done explicitly.** `Ticket.assignedToId`'s `onDelete: SetNull` (schema.prisma) only fires on a real row delete — since a soft delete never removes the row, it never fires. `DELETE /api/users/:id` unassigns every ticket currently assigned to the target (`prisma.ticket.updateMany({ where: { assignedToId: userId }, data: { assignedToId: null } })`) in the same `$transaction` as the `deletedAt` update, so a deleted user never lingers as a ticket's assignee. Follow this same pairing — soft-delete the row, and explicitly null out every FK elsewhere that assumed a real `onDelete` cascade would handle it — for any other soft-deletable resource with incoming FKs.

For confirming a destructive action, use shadcn's `alert-dialog.tsx` (`role="alertdialog"`, not `dialog.tsx`'s `role="dialog"`) rather than the plain `Dialog` — see `DeleteUserDialog.tsx`. One non-obvious bit of its wiring: `AlertDialogAction` is a `Dialog.Close` under the hood, so a plain `onClick` still closes the dialog immediately regardless of whether your mutation succeeds. Call `event.preventDefault()` in the action's `onClick` and close manually (via the `onOpenChange` prop passed down, same as `EditUserDialog`) only from the mutation's `onSuccess` — otherwise a failed delete silently closes the confirmation instead of showing the error.

### Error handling

Express 5 automatically forwards a rejected promise from an `async` route handler to the error-handling middleware — unlike Express 4, you don't need to wrap the handler body in `try/catch` (or a `catchAsync`-style helper) just to keep the process from crashing on an unhandled rejection. The handlers in `server/src/routes/users.ts` (`POST /api/users`, `GET /api/users`) let Prisma/zod errors propagate this way.

Only reach for `try/catch` when you need to turn a specific failure into a specific response, rather than the default error handling. `GET /api/health` is the example: it catches so it can report `503 { status: "error", database: "unreachable" }` instead of a generic 500, since the probe's whole purpose is distinguishing "DB unreachable" from "server down."

On the client, every mutation's `onError` needs to pull that server-provided `{ error: string }` message out of a failed request, falling back to a generic message for anything else (a network failure, an unexpected response shape). Use `getErrorMessage(error, fallback)` from `client/src/lib/api-error.ts` for this rather than inlining `axios.isAxiosError(error) && error.response?.data?.error` again — see its usage in `UserForm.tsx`, `DeleteUserDialog.tsx`, and `ReplyForm.tsx`.

Render that message with `<ErrorMessage message={error} />` (`client/src/components/ErrorMessage.tsx`) rather than the `{error && <p role="alert" className="text-sm font-normal text-destructive">{error}</p>}` block inline — it renders nothing for a `null`/empty message, so callers don't need their own `{error && ...}` guard. This is the whole-form/whole-mutation counterpart to `FieldError` (`components/ui/field.tsx`), which renders one field's react-hook-form validation errors instead. `LoginPage.tsx`, `UserForm.tsx`, `DeleteUserDialog.tsx`, and `ReplyForm.tsx` all use it this way.

The same component also covers a `useQuery`'s fetch failing outright — a whole-view error with no form or mutation involved. `UsersTable.tsx`, `TicketsTable.tsx`, `TicketDetailPage.tsx`, and `DashboardStats.tsx` all render `<ErrorMessage message="Could not load X — is the server running?" />` in their `isError` branch instead of a duplicated `<p className="text-destructive">...</p>`, passing a fixed string rather than a value pulled from the error itself (`getErrorMessage` is for a caught mutation error's response body; a failed `useQuery` here doesn't need that distinction — the message is always the same static "is the server running?" hint).

### Rate limiting

Two layers, both IP-keyed:

- **`/api/auth/*`** (sign-in, sign-up, session, etc.): better-auth's built-in limiter (`server/src/lib/auth.ts`), forced on in all environments (`enabled: true`) rather than its "production only" default, so dev/test behavior matches prod. Sign-in/sign-up/password-change get a stricter built-in 3-requests/10s rule automatically; everything else under `/api/auth` gets the configured 100/60s default. Counters are stored in Postgres (`rate_limit` table, added by the `add_rate_limit_table` migration) rather than in-memory, so counts stay correct across multiple server instances — no Redis dependency needed just for this.
- **Everything else** (`/api/hello`, `/api/me`, `/api/users`): `express-rate-limit`, 100 requests/60s, in-memory. The limiter (`apiLimiter`) is defined once in `server/src/middleware/rate-limit.ts` and applied per-route in `server/src/index.ts` (`/api/hello`) and `server/src/routes/users.ts` (`/api/me`, `/api/users`). `/api/health` is deliberately excluded — it's an infra health probe (ALB target group) and must not be throttled.

Both need the real client IP to key correctly, which only works if two things are set per environment:

- **`NODE_ENV`** — must be `development`/`test`/`production` (set in `server/.env`, `server/.env.test`, and the production task definition respectively). Without it, better-auth's own IP resolution can't identify local requests and every client collapses into one shared bucket per path — a real correctness bug, not just a missing nicety.
- **`TRUSTED_PROXY_CIDRS`** — comma-separated CIDR list of trusted proxies, read by both `app.set("trust proxy", ...)` in `index.ts` and better-auth's `advanced.ipAddress.trustedProxies` in `auth.ts`. Empty in dev/test (no proxy in front locally). In production, set it to the VPC CIDR the ALB forwards from (see `tech-stack.md`'s deployment section) — without it, `X-Forwarded-For` isn't trusted and every request behind the ALB looks like it comes from the same place.

The sign-in endpoint's 3-requests/10s limit applies to server tests too (rate limiting is forced on in every environment, including `test`), and every real sign-in across a single `bun test` run shares the same counter — `tickets.test.ts` and `users.test.ts` between them are already at that budget. A new server test needing an authenticated session should reuse an existing signed-in `agent` from whichever `describe` block already covers that role, rather than adding another real sign-in call; see the comments on `tickets.test.ts`'s `"a single-ticket-scoped session"` describe and `users.test.ts`'s `"DELETE /api/users/:id"` describe (the latter also resets the `rate_limit` table before its sign-in, having genuinely needed a 4th).

### Testing strategy: component tests first, e2e only when necessary

**Default to a component test — client (Vitest + RTL) or server (`bun:test` + `supertest`, see "Server testing" below) — and reach for `e2e/` only when the behavior genuinely can't be verified without a real browser.** Most of what needs covering fits the former: a component's loading/error/empty/populated states, form validation, a route's auth/validation/response-shape logic. It's not just style — component/server tests run in milliseconds to a few hundred ms with everything mocked or hit directly, where the e2e suite needs a live Postgres, two dev servers, and an actual browser, and takes 10+ seconds per run.

Reach for `e2e/` when a component test structurally can't cover it: real page navigation and client-side routing, a redirect, a cookie/session persisting across a reload, or a flow that genuinely spans client and server together in a way a mocked-`axios` component test can't represent. When a new test is needed, default to writing it as a component/server test first; add an e2e spec only for the specific slice of behavior that requires a browser, not the whole flow.

This is also why `server/src/routes/tickets.test.ts` replaced the original `e2e/tests/ticket-ingestion.spec.ts` for `POST /api/tickets`: that endpoint's behavior (secret-header check, zod validation, response shape) is pure request/response logic with no browser involved, so it moved to a server test once that harness existed.

### Component testing

Client component tests use Vitest + React Testing Library, jsdom environment. Config lives in `client/vite.config.ts`'s `test` block (`/// <reference types="vitest/config" />` at the top of that file makes the `test` key available on `defineConfig` from `vite`); global setup is `client/src/test/setup.ts` (registers `@testing-library/jest-dom/vitest` matchers and calls RTL's `cleanup()` in `afterEach` — required because the config doesn't set `globals: true`, so every test file imports `describe`/`it`/`expect`/etc. from `vitest` explicitly rather than relying on ambient globals).

When writing a new spec:

- **Location & naming**: colocate as `Component.test.tsx` next to the component it tests (e.g. `client/src/pages/UsersPage.tsx` → `client/src/pages/UsersPage.test.tsx`), not in a separate `__tests__` tree.
- **Data fetching**: don't hit the real API. `vi.mock("axios")` at the top of the file, then `vi.mocked(axios, true)` to get a typed mock and set per-test behavior with `mockResolvedValue`/`mockRejectedValue`/`mockReturnValue` (reset in `beforeEach` so tests don't leak mock state into each other).
- **TanStack Query components**: any component using `useQuery`/`useMutation` needs a `QueryClientProvider` ancestor in the test render — use the `renderWithQuery` helper from `client/src/test/render-with-query.tsx` instead of hand-rolling a `QueryClient` per test file. It wires up a fresh client per render with `retry: false` (so a mocked rejection surfaces immediately instead of retrying and timing out the test).
- **Async assertions**: query pending/loaded/error states with RTL's `findBy*`/`findAllBy*` (they wait), not `getBy*` immediately after a fetch-triggering render.
- **Ambiguous text matches**: shadcn components often duplicate visible text (e.g. a table column header and a badge in that column can both say "Verified") — disambiguate with `getByText(text, { selector: "span" })` or scope with `within(row)` rather than reaching for `getAllByText` and indexing blindly.
- **Radix `Select`**: jsdom doesn't implement `hasPointerCapture`/`setPointerCapture`/`releasePointerCapture`/`scrollIntoView`, which Radix's `Select` calls on open — `client/src/test/setup.ts` stubs all four globally, so you shouldn't need to touch that again. To actually pick a value in a test, drive the real interaction (`fireEvent.click` the trigger via `getByLabelText`, then `fireEvent.click` the option via `findByRole("option", { name })`) rather than `fireEvent.change` — it isn't a native input. See `selectRole` in `client/src/pages/UserForm.test.tsx`.

`client/src/pages/UsersTable.test.tsx` is the reference example for all of the above (loading-skeleton state, populated table, empty state, error state).

### Server testing

Server tests use Bun's built-in test runner (`bun:test` — `describe`/`test`/`expect`, Jest-compatible matchers including `toMatchObject`) plus `supertest` against the Express `app` directly, **not** Playwright/the e2e harness — per "Testing strategy" above, this is where a route's auth/validation/response-shape logic belongs.

- **The app must be importable without binding a port**: `server/src/app.ts` exports the fully configured `app` (all middleware/routes); `server/src/index.ts` is a thin two-line entry point that imports it and calls `app.listen(...)`. Tests import `app` from `app.ts` and drive it with `supertest(app)` — never import `index.ts`, which would bind a real port as a side effect.
- **Database**: tests run against the same `helpdesk_test` database the e2e suite uses (`bun --env-file=.env.test test`, per `server/package.json`'s `test` script — this is what loads `EMAIL_INGEST_SECRET`, `DATABASE_URL`, etc. from `.env.test`), not a mocked Prisma client. Unlike the e2e database, don't let rows accumulate: track anything a test creates and delete it in `afterAll` (see `createdTicketIds` in `routes/tickets.test.ts`).
- **Location & naming**: colocate as `Route.test.ts` next to the route file it tests (e.g. `server/src/routes/tickets.ts` → `server/src/routes/tickets.test.ts`), mirroring the client's colocation convention.

`server/src/routes/tickets.test.ts` is the reference example (auth-header checks, zod validation, response shape, and the cleanup pattern above).

The root-level docs describe the target product and are well ahead of what's implemented:

### Tickets: deliberately minimal, email ingestion still unresolved

`Ticket` (`schema.prisma`) exists but only as much as `project-scope.md`'s *settled* decisions require: `id` is a numeric autoincrement (not the string/UUID `id` pattern every other model in this schema uses), `status` (`OPEN`/`RESOLVED`/`CLOSED`, per the ticket-statuses decision), an optional `category` (`TicketCategory`: `GENERAL_QUESTION`/`TECHNICAL_QUESTION`/`REFUND_REQUEST`, per the categories decision) with **no default** — it's `null`/unset until AI classification actually runs, not defaulted to a guess, since nothing populates it yet (that's a later implementation-plan phase), and an optional `requesterName` (per the "Requester display name" decision — display-only plus reply-personalization, not required since it isn't always resolvable). No Message-ID/threading fields — reply-threading strategy is still an open question, unlike ticket categories (or the requester name) which are already decided. Don't add ingestion/threading fields without a decision recorded in `project-scope.md` first, per the rule above.

**`POST /api/tickets`** (`server/src/routes/tickets.ts`) is how a ticket gets created from an email today: it accepts `{ from, requesterName?, subject?, body }` and inserts a `Ticket`. It does **not** talk to a real mailbox — `project-scope.md`'s "Email ingestion" open question (Gmail API vs. Microsoft Graph vs. generic IMAP vs. an inbound-parse webhook provider) is still unresolved, so this endpoint is the provider-agnostic landing point a real integration will call into once that's decided, not the integration itself.

Because the real caller here is a webhook (an email provider's server), not a signed-in browser, this route is gated by a shared secret (`EMAIL_INGEST_SECRET` env var, checked against the `x-ingest-secret` request header) instead of `req.user`/session auth like every other mutating route in this codebase. Follow that same pattern — not session auth — for any other endpoint whose real caller is a system, not a person: check the header against the env var and **fail closed if the env var itself is unset** (`if (!expectedSecret || header !== expectedSecret)`, not just `header !== expectedSecret` — the latter silently passes when both sides are `undefined`).

**`GET /api/tickets`** is the one exception to "gate reads/writes to ADMIN" that every `users.ts` route follows: it only requires `req.user` to exist, no role check, per `project-scope.md`'s "Agent permissions" decision (regular agents have full ticket control, not just admins). `/tickets` (`TicketsPage.tsx`/`TicketsTable.tsx`, following the same page/data-component split as `UsersPage.tsx`/`UsersTable.tsx`) is routed under `ProtectedRoute` in `App.tsx`, not `AdminRoute` like `/users` — same reasoning. `TicketStatus`/`TicketCategory` are exported from `core` (`core/src/schemas/ticket.ts`) as the same const-object "enum" pattern as `Role`, for the same reason: `client` needs magic-string-free values for badge rendering, and `core` can't depend on Prisma's generated output.

**Sorting, filtering, and pagination are all server-side** — `TicketsTable.tsx` renders whatever `GET /api/tickets` returns rather than sorting/filtering/paginating the fetched page itself. This is why the endpoint returns `{ tickets, total, page, pageSize }` rather than just `tickets`: `total` is the full (filtered) count across all pages, needed to compute how many pages exist, since the client only ever holds one page's worth of rows.

- **Sorting**: via TanStack Table in `manualSorting` mode. `useReactTable`'s `SortingState` (one column, `enableMultiSort: false`/`enableSortingRemoval: false` so it's always exactly `[{ id, desc }]`, never empty or multi-column) drives the `useQuery`'s `sortBy`/`sortOrder` params directly — clicking a column header changes `sorting`, which changes the query key, which triggers a refetch with the new params. The endpoint validates `sortBy` against an explicit allow-list of real `Ticket` columns (`id`/`subject`/`requesterEmail`/`status`/`category`/`createdAt`) before it ever reaches `prisma.ticket.findMany`'s `orderBy` — it's a real HTTP query param any caller can set, so an un-validated value would let an arbitrary/invalid field name through to Prisma.
- **Filtering**: plain `Select` dropdowns (status, category) above the table, each backed by its own `useState`, also included in the `useQuery` key/params. An `"ALL"` sentinel means "no filter" (omit the param entirely) rather than sending an empty string — Radix's `Select.Item` can't take `""` as a value, since that's reserved for "nothing selected." A second sentinel, `"UNCLASSIFIED"`, means "`category` is `null`" — a query param can't express `null` any other way, so the server (`server/src/routes/tickets.ts`) special-cases that exact string to `{ category: null }` in the Prisma `where`, and it's a real `z.literal("UNCLASSIFIED")` in the validation schema alongside `z.nativeEnum(TicketCategory)`, not an unchecked passthrough.
- **Date-range filtering**: two native `<input type="date">` elements (`createdFrom`/`createdTo`, each its own `useState<string>`, `""` for unset) alongside the `Select` filters, same pattern — included in the `useQuery` key, omitted from `params` entirely when empty rather than sent as `""`. The wire format is the input's own native value, plain `"YYYY-MM-DD"`; no client-side `Date` parsing needed since the string round-trips straight to the query param. Server-side, `z.coerce.date()` parses that string as UTC midnight, so `createdFrom` (used as `gte`) is naturally inclusive of its whole day, but `createdTo` used bare as `lte` would only include that day's first instant — the route expands it to `23:59:59.999` UTC (an `endOfDay` helper) before building the Prisma `where`, so the end date is inclusive too. A `.refine` on the query schema 400s if `createdFrom` is after `createdTo`, rather than silently returning an empty result set for a swapped range.
- **Pagination**: TanStack Table in `manualPagination` mode — `PaginationState` (`pageIndex`, 0-indexed; `pageSize`, default 10) drives `page`/`pageSize` query params (`page` is 1-indexed over the wire — the `+ 1`/`- 1` conversion happens at the query-building boundary, not in state). `pageCount` is computed from the response's `total` (`Math.ceil(total / pageSize)`) and passed back into `useReactTable` so `table.getCanNextPage()`/`getCanPreviousPage()` work correctly. `pageSize` is capped server-side at 100 (`z.coerce.number().max(100)`) so a caller can't force-load the whole table in one request. **Changing sort or a filter resets `pageIndex` to 0** — otherwise the user can get stranded on a page number that doesn't exist for the new result set.

Follow this same shape (`ColumnDef` column ids / filter values matching a server-side allow-list, `manualSorting`/`manualPagination: true`, sort+filter+pagination state all in the query key, reset to page 1 on sort/filter change) for any other list that needs sortable/filterable/paginated columns — don't reach for TanStack Table's built-in client-side sorting/filtering/pagination (`getSortedRowModel`/`getFilteredRowModel`/`getPaginationRowModel`) for data that shouldn't be fully loaded client-side just to slice, sort, or filter it.

**Ticket detail page**: `TicketsTable.tsx`'s subject cell is a `react-router-dom` `Link` to `/tickets/:id` (`TicketDetailPage.tsx`, routed in `App.tsx` under `ProtectedRoute` alongside `/tickets`), which fetches the single ticket via `GET /api/tickets/:id` (`server/src/routes/tickets.ts`) — same `req.user`-only access rule as the list endpoint, no role check. The list endpoint's `TicketListItem` (`TicketsTable.tsx`) intentionally omits `body`/`updatedAt`, since a paginated list response shouldn't carry a field only the single-ticket view needs; the full shape (`Ticket`, including `body`) plus the `categoryLabels`/`statusBadgeVariant` display maps live in `client/src/lib/ticket-display.ts` so the list and detail views can't render a status/category differently. `:id` is validated with `z.coerce.number().int().positive()` against the route param (400 if it isn't numeric — `Ticket.id` is a numeric autoincrement, unlike `User.id`) before the `prisma.ticket.findUnique` lookup, which 404s if nothing matches.

Testing this needed `client/src/test/render-with-query.tsx` (the shared `renderWithQuery` test helper) to also wrap renders in a `MemoryRouter` — any component reaching for `Link` (now including `TicketsTable.tsx`) throws without a `Router` ancestor. A component that reads route state itself, like `TicketDetailPage.tsx`'s `useParams`, needs the `ui` passed to `renderWithQuery` wrapped in its own `<Routes><Route path="/tickets/:id" element={...} /></Routes>`, with the target path passed via the helper's `initialEntries` option — see `TicketDetailPage.test.tsx`.

`TicketDetailPage.tsx` itself is just the data-fetching shell: the two `useQuery` calls (the ticket, and `GET /api/users/assignable`) and the `isPending`/`isError` branches. The loaded content is four sibling components, each taking the loaded `ticket: Ticket` as a single prop rather than a handful of individual fields (same reasoning as `UserForm`'s discriminated-union prop over several loose ones — one object, not a props-shaped duplicate of it): `TicketDetails.tsx` (subject/id, sender, created date, body — deliberately no reply-thread content), `UpdateTicket.tsx` (the Status/Category/Assigned-to `Select`s, described below), and `ReplyForm.tsx` (described in "Error handling" above). `TicketDetailsSkeleton.tsx` is the `isPending` placeholder, swapped in before any of these render. The reply thread itself (the `data.replies.map(...)` block) is small enough to stay inline in `TicketDetailPage.tsx` rather than becoming a fifth component. Follow this same split for any other detail page: a thin page-level data shell, with each visually distinct region as its own component taking the loaded entity as one prop, not the page threading individual fields down.

Because `ReplyForm.tsx` and `UpdateTicket.tsx` only receive that loaded `Ticket` object — not the page's `:id` route param — their own `invalidateQueries` calls key off `ticket.id`, which is a `number`. `TicketDetailPage.tsx`'s own query has to key off that same numeric form too (`const ticketId = Number(id)`, not the raw string route param from `useParams`) for the two to invalidate the same cache entry: TanStack Query's key matching is type-strict (`5 !== "5"`), so a query keyed `["ticket", "5"]` is invisible to `invalidateQueries({ queryKey: ["ticket", 5] })` — the reply/update mutation would silently no-op instead of refetching the ticket. Follow this — coerce a route param to whatever type a child component's own data naturally carries, rather than leaving the two representations to drift — for any other page that splits a `:id`-keyed query's mutations out into components this way.

**Ticket assignment**: `Ticket.assignedToId` (nullable, `onDelete: SetNull`) is a plain FK to `User` — `assignedTo` (`{ id, name, email }`, via `include` on both `GET /api/tickets` and `GET /api/tickets/:id`) is the populated shape both the list's Assignee column and the detail page's picker render. `PATCH /api/tickets/:id/assign` (body `{ assignedToId: string | null }`, `null` unassigns) does the reassignment; per `project-scope.md`'s "Agent permissions" decision this is `req.user`-only like every other ticket endpoint, not ADMIN-gated — any authenticated user can reassign any ticket. It 404s if the ticket doesn't exist, and separately 404s (`"Assignee not found"`) if `assignedToId` is set but doesn't resolve to a non-soft-deleted `User`.

`assignedToId` validation is two-layered, both required: the zod schema (`z.string().min(1).nullable()`) rejects `""` outright rather than accepting any string, and the handler checks existence with `assignedToId !== null` rather than a truthy check — a truthy check would let an empty string (if it ever got past the schema some other way) skip the `prisma.user.findUnique` lookup and hit `prisma.ticket.update` directly, where a nonexistent id fails as an opaque FK-constraint 500 instead of the clean `404 "Assignee not found"` every other invalid-assignee case returns. Follow this same two-layer shape (schema rejects the empty/degenerate value, handler existence-checks with the real "did the caller mean to omit this" condition rather than JS truthiness) for any other nullable-FK-by-id body field.

**Updating status/category**: `PATCH /api/tickets/:id` (distinct from `PATCH /api/tickets/:id/assign` — a general ticket update vs. the assignment relation specifically) takes `{ status?, category? }`, both independently optional so a caller can change either field alone or both together in one request; `updateTicketSchema`'s `.refine` 400s if neither is present, rather than silently no-opping. `category` is nullable *and* optional — omitted means "leave it," explicit `null` means "clear it back to unclassified" (overriding an AI classification, per `project-scope.md`'s "Agent permissions" decision), `status` has no such unset state since a ticket always has one. Same access rule as every other ticket endpoint: `req.user`-only, not ADMIN-gated. On the client, `UpdateTicket.tsx` (rendered by `TicketDetailPage.tsx` as the right-hand column, taking `ticket` and `assignableUsers` as props) is where Status and Category are `Select`s (not the read-only `Badge`/text `TicketsTable.tsx` still uses in its list columns) sharing one `updateTicket` mutation — each `onValueChange` calls `updateTicket.mutate({ status })` or `updateTicket.mutate({ category })` with only its own field, matching the endpoint's partial-update semantics; `"UNCLASSIFIED"` is the same kind of client-only sentinel as `TicketsTable.tsx`'s filter and the assignee picker's `"UNASSIGNED"`. The three `Select`s share a `SidebarField({ label, children })` wrapper local to `UpdateTicket.tsx`, since they were otherwise identical apart from the label and the `Select` itself.

Populating the "assign to" picker needed a users endpoint any authenticated user (not just admins) can call, so `GET /api/users/assignable` (`server/src/routes/users.ts`) exists alongside the ADMIN-only `GET /api/users` — deliberately minimal (`id`/`name`/`email` only, no `role`/`emailVerified`/`createdAt`) rather than reusing the admin list's shape with looser permissions. Follow this same split — a separate, minimally-shaped, non-admin-gated endpoint — for any other case where a non-admin flow needs to reference "a user" without needing the full admin user-management view. `TicketDetailPage.tsx` fetches this list and passes it down; `UpdateTicket.tsx` itself doesn't fetch.

`UpdateTicket.tsx`'s assignee `Select` is a direct-mutate control, not a form: `onValueChange` calls `assignTicket.mutate(...)` straight away (no submit button), same as `TicketsTable.tsx`'s filter `Select`s triggering a requery on change. `"UNASSIGNED"` is the sentinel for "no assignee" (same reasoning as `TicketsTable.tsx`'s `ALL`/`UNCLASSIFIED` — Radix's `Select.Item` can't use `""`). On success it invalidates both `["ticket", ticket.id]` and, via TanStack Query's key-prefix matching, every `["tickets", ...]` list query, so the Assignee column stays in sync if the user navigates back without an explicit refetch call. Asserting a mutation's request body in a test needs `await waitFor(...)`, not a synchronous `expect` right after the triggering `fireEvent` — `mutate()` (unlike an inline-`await`ed `mutateAsync`) doesn't run its `mutationFn` before the next line executes; see `UpdateTicket.test.tsx`'s assignment tests and the pre-existing pattern in `EditUserDialog.test.tsx`.

### Reply drafting and polishing

`ReplyForm.tsx` has two AI buttons before "Send reply": "Generate reply" drafts one from scratch, grounded only in the ticket's own subject/body, for when there's no draft yet; "Polish" improves the agent's current draft in place (disabled while the draft is empty, since there's nothing to polish). Both hit their own endpoint, get back `{ body }`, and swap it into the form via `setValue("body", result, { shouldValidate: true, shouldDirty: true })` — neither persists or sends anything; the agent still reviews the result and clicks "Send reply" themselves. This is a lighter-weight, human-in-the-loop writing assist, not `project-scope.md`'s planned autonomous AI reply system (which drafts and sends without review by default) — don't conflate the two, and don't let either button's existence be read as satisfying that roadmap item.

Because of that distinction, this deliberately does **not** use `tech-stack.md`'s Anthropic Claude pick for the full system: `server/src/lib/reply-drafting.ts` calls Google's Gemini (`gemini-3.5-flash-lite`) via the Vercel AI SDK (`ai`'s `generateText` + `@ai-sdk/google`'s `google(...)` model), chosen for this narrow feature specifically because Google AI Studio's free tier covers it at zero cost, unlike Claude or OpenAI. Requires `GOOGLE_GENERATIVE_AI_API_KEY` (`server/.env`, not committed — see its comment for how to get a free key); the `@ai-sdk/google` provider reads this env var itself, no explicit wiring needed. Google has already retired one model id this feature relied on (`gemini-2.0-flash-lite`, mid-2026) — if `generate-reply`/`polish-reply` start 502ing, check the `AI_APICallError` in the server log before assuming the key is bad; it names the current model to switch to. If this feature is ever consolidated into the real Claude-based system, revisit this provider choice then rather than adding a second one in parallel.

Both routes (`server/src/routes/tickets.ts`) are `req.user`-only like every other ticket endpoint (no ADMIN gate) and fetch the ticket for context (its `subject`/`body` go into the prompt, so the AI is grounded in what's actually being replied to, not just improvising) before calling into `lib/reply-drafting.ts`. `generate-reply` takes no request body — the ticket itself is the only input — while `polish-reply` validates `:id` and `polishReplySchema`'s `{ body }` (`core/src/schemas/ticket.ts`, next to `TicketStatus`/`TicketCategory` — same non-empty-string shape as `createReplySchema` in `reply.ts`, since a blank draft can't be polished either) the same way `POST /api/tickets/:id/replies` does. `generateReply`'s system prompt explicitly forbids inventing order/account/refund specifics the model has no access to (it should say the agent will look into it, not fabricate a confident-sounding answer) — this matters more for generation than polishing, since polishing only touches wording the agent already wrote. Unlike the rest of this file's Prisma/zod-only handlers, both **do** wrap the AI call in `try/catch` (per the "Error handling" section's rule: reach for `try/catch` when a specific failure needs a specific response) — an unreachable/erroring/misconfigured AI provider is a `502` with a clean message, not a generic 500.

Both functions sign their output before returning it — `lib/reply-drafting.ts`'s `signReply(text, agentName)` appends `"\n\nBest regards,\n{agentName}\nCodeWithMosh Support\nhttps://codewithmosh.com"` — rather than asking the model to include a sign-off in its own output, which would need trusting it to get the name/team/link right, consistently, every time. `agentName` is `req.user.name` from the caller's own session, not client input. Both system prompts also explicitly tell the model not to add its own sign-off, so the two don't end up doubled up. `evaluateAutoResolution` (see "Ticket auto-resolution" below) uses the same `signReply`, with `agentName` set to "AI Assistant" rather than a real session's name.

All three reply-producing prompts (`polishReply`, `generateReply`, `evaluateAutoResolution`) also share one `TONE_AND_FORMATTING_GUIDANCE` string — a professional, customer-friendly tone and short paragraphs with blank lines between them, rather than one dense block of text — so the three can't drift into inconsistent voice/formatting over time the way three separately-written phrasings would.

The greeting at the *other* end of the reply — addressing the customer — works the opposite way: it's left to the model, not deterministically inserted, since (unlike the agent's fixed sign-off) it has to read naturally as part of the drafted/polished text. `Ticket.requesterName` (schema.prisma, nullable — the email ingestion webhook may not resolve a display name, and pre-existing tickets have none) is passed to both functions as `customerName`; `lib/reply-drafting.ts`'s `firstNameOf()` takes just the first token of it (never the full name — "Hi Isabella," not "Hi Isabella Moreau,") and both system prompts are told explicitly to use only that first name if present, or fall back to a generic greeting like "Hi there," rather than invent one when `customerName` is `null`. `POST /api/tickets` (the ingestion endpoint) accepts an optional `requesterName` in its request body for this; `TicketDetails.tsx` also renders it (`"{name} <{email}>"`, falling back to just the email) so it isn't AI-only plumbing invisible in the UI.

Testing this needed `bun:test`'s `mock.module` (`server/src/routes/tickets.test.ts`) to replace `lib/reply-drafting.ts`'s and `lib/ticket-analysis.ts`'s exports (one `mock.module` call per file, since they're two separate modules — see below), so both routes' request/validation/response-shape logic can be tested without a real network call or API key — and, just as importantly, without spending another slot in the sign-in endpoint's shared 3-requests/10s test budget (see "Rate limiting" above): the new tests are nested inside the existing `"a single-ticket-scoped session"` describe, reusing its already-authenticated `agent` rather than signing in again. `mock.module` works here specifically because it retroactively replaces the module for consumers (`tickets.ts`) that had already imported it by the time the mock is registered — it doesn't need to run before that import, unlike Jest's hoisted `jest.mock`. Each mock factory has to provide *every* export its real module has (`lib/reply-drafting.js`'s `polishReply`/`generateReply`; `lib/ticket-analysis.js`'s `summarizeTicket`), even in a test that only exercises one — an omitted export is `undefined` in `tickets.ts` and crashes the other routes instead of just leaving it untested. Because these mocks replace the functions wholesale, they never exercise their real internals (`signReply`, `firstNameOf`, `summarizeTicket`'s transcript-building) — `reply-drafting.ts`'s own `reply-drafting.test.ts` and `ticket-analysis.ts`'s own `ticket-analysis.test.ts` cover that instead, mocking one level deeper (the `ai` package's `generateText`/`generateObject` and `@ai-sdk/google`'s `google`) so the real, exported functions run for real and their behavior is asserted on actual return values and prompt content.

`lib/ai.ts` used to hold all five of these functions in one file; it's since been split along a customer-facing-vs-internal line: `lib/reply-drafting.ts` owns the low-level shared pieces (`model`, `signReply`, `firstNameOf`, `TONE_AND_FORMATTING_GUIDANCE`) plus the two customer-facing draft functions (`polishReply`, `generateReply`); `lib/ticket-analysis.ts` owns the three internal-only functions (`summarizeTicket`, `classifyTicket`, `evaluateAutoResolution`, plus the exported `AI_ASSISTANT_NAME` constant) and imports the shared pieces it needs (`model`, `signReply`, `firstNameOf`, `TONE_AND_FORMATTING_GUIDANCE`) from `reply-drafting.ts` rather than duplicating them — `evaluateAutoResolution` is the one internal function that still needs the same sign-off/greeting behavior as the customer-facing pair. Follow this same "one importable module with the shared primitives, a second depending on it for a distinct concern" shape rather than a third catch-all/shared file, if `ai.ts`'s functions ever need splitting again.

### Ticket summarization

`TicketSummary.tsx`, rendered directly below `TicketDetails.tsx` (so it sits right under the ticket's own message, per the "below the message" placement it was built to), is a "catch me up" tool for the agent: a "Summarize" button (`SparklesIcon` from `lucide-react`) hits `POST /api/tickets/:id/summarize`, which returns `{ summary }` covering both the ticket's original message and its reply thread so far. Unlike `ReplyForm`'s two AI buttons, nothing here feeds into a form — the summary is just rendered in a box below the button, for the agent to read, not edit or send.

**Deliberately not cached or persisted, client or server side** — every click is a fresh `POST`, no `staleTime`/query-key reuse, and the server doesn't store the result anywhere. The button relabels itself "Regenerate summary" once one exists, making it clear a click always produces a new one rather than replaying a cached result — this matters because the reply thread can grow between clicks (a customer or another agent replies), and a summary is far more likely to go stale than an agent's own draft reply text is.

The route (`server/src/routes/tickets.ts`) fetches the ticket *with* its `replies` (`include`, same shape as `GET /api/tickets/:id`) rather than just `subject`/`body` like `polish-reply`/`generate-reply` do, and maps each to `{ senderType, authorName, body }` for `lib/ticket-analysis.ts`'s `summarizeTicket()`. Its system prompt is explicit that this is an internal note for the agent, not a customer-facing message — no greeting, no sign-off, don't address anyone by name — the opposite framing from `generateReply`'s prompt, since this text is never meant to be sent anywhere.

### Ticket classification

`POST /api/tickets` (the email ingestion webhook) classifies a new ticket's `category` automatically, non-blockingly, via a real job queue: right after `prisma.ticket.create`, it `await`s `lib/queue.ts`'s `enqueueClassifyTicket(ticket)` — a fast insert into pg-boss's own job table, not the AI call itself — then responds `201`. The response's `ticket.category` is therefore always `null`; the real value lands via a separate `prisma.ticket.update` once the queued job actually runs, so a caller that needs the classified category has to `GET` the ticket again afterward.

**pg-boss**, not BullMQ, backs this queue — it's a job queue built directly on Postgres (its own `pgboss` schema in the same database `DATABASE_URL` already points at), needing no separate Redis dependency. Same reasoning as this codebase's rate limiter storing counts in a Postgres table instead of Redis (see "Rate limiting" above), and the same non-blocking outcome implementation-plan.md's Phase 3 "Classification worker (BullMQ job)" describes, without committing to BullMQ specifically. This also does **not** implement confidence scoring, the escalation queue, or the `ai_actions` audit table — those remain project-scope.md's open questions (`Confidence threshold`, `PII guardrails specifics`) and are out of scope here; `classifyTicket` always commits to one of the three `TicketCategory` values, with no low-confidence fallback.

`lib/queue.ts` owns the queue itself: `enqueueClassifyTicket(ticket)` sends the job (`{ ticketId, subject, body }`); `processClassifyTicketJobs(jobs)` is the worker — registered via `boss.work(...)` inside `startQueue()`, but exported and callable on its own so it's testable without a real or heavily mocked `PgBoss` instance driving it. It loops over the batch and catches each job's error individually, so one ticket's classification failing doesn't fail every other job pg-boss handed it in the same batch (a rejected batch handler fails every job in it). `startQueue()` itself — `boss.start()`, `createQueue()`, then `work()` — is called once from `index.ts`, not `app.ts`: `app.ts` has to stay side-effect-free for tests (same reasoning it never calls `app.listen()` either), so `tickets.test.ts` mocks `lib/queue.ts`'s `enqueueClassifyTicket` wholesale rather than ever starting a real queue.

`lib/ticket-analysis.ts`'s `classifyTicket()` uses `generateObject({ output: "enum", enum: [...] })` rather than `generateText` — the model is constrained to return exactly one of `TicketCategory`'s three values (Prisma's own generated enum, not core's re-declaration — see "Core enums" above), not free text that would need parsing/validation.

Server tests needed `--isolate` added to `server/package.json`'s `test` script (`bun test --isolate`) once a *third* file started mocking the same AI module (back when this all lived in one `lib/ai.ts`): by default `bun test` shares one module registry across every file in a run, so `mock.module` calls collide across files targeting the same resolved path (last-registered mock wins for every consumer, in every file) — the module's own test file needs the real implementation (with `generateText`/`generateObject` mocked underneath it), while `tickets.test.ts` and `queue.test.ts` each separately mock it wholesale for their own routes/worker. `--isolate` gives every test file its own registry, so each file's mocks only ever affect that file — do this from the start for any new server test file that mocks a module another file also touches, rather than rediscovering the collision. This still applies post-split: `queue.test.ts` mocks `./ticket-analysis.js` wholesale, `tickets.test.ts` mocks both `../lib/reply-drafting.js` and `../lib/ticket-analysis.js` wholesale, while `reply-drafting.test.ts` and `ticket-analysis.test.ts` each exercise their own module's real code with only `ai`/`@ai-sdk/google` mocked underneath.

### Ticket auto-resolution

Every new ticket is also judged, non-blockingly (`enqueueAutoResolveTicket`, a second pg-boss queue alongside `classify-ticket` — see "Ticket classification" above for the non-blocking/durable reasoning, identical here), for whether it can be answered with **no human at all**: `lib/ticket-analysis.ts`'s `evaluateAutoResolution()` returns `{ resolvable, reply }` in one `generateObject` call (schema mode, not enum mode — the shape isn't a single fixed set of values). If `resolvable` and `reply` are both truthy, `lib/queue.ts`'s `processAutoResolveTicketJobs` sends that reply and sets `status: RESOLVED` **immediately, with zero review step** — this is genuinely different from every other AI tool in this file: `ReplyForm`'s two buttons and `TicketSummary` all put a human between the AI's output and anything real happening, this one doesn't. This is the first actual instance of project-scope.md's "AI autonomy" decision (autonomous, no review step by default), not another human-assist tool predating it — see project-scope.md's "Autonomous auto-resolution" decision for what it deliberately does *not* implement yet (a numeric confidence threshold, an escalation queue).

Because of that, `evaluateAutoResolution`'s system prompt is deliberately conservative — told explicitly to default to `resolvable: false` whenever unsure, and that it has no access to order/account/refund systems (same constraint as `generateReply`'s prompt), since a wrong autonomous answer is far worse than a human-reviewed one being merely mediocre. `classifyTicket` and `evaluateAutoResolution` run as two independent, parallel jobs from the same `POST /api/tickets` call, not a chained pipeline — whether a ticket gets auto-resolved doesn't depend on its classification finishing first (or at all).

`TicketReply.authorId` still requires a real `User` (no AI-facing reply path exists at the schema level — see its own comment in `schema.prisma`), so an autonomously-sent reply needs a real row to attribute itself to. `lib/queue.ts`'s `getOrCreateAiAssistantUser()` lazily upserts one, by a fixed well-known email (`ai-assistant@internal.helpdesks`), the first time any job actually needs it — not via `prisma/seed.ts`, so this works the same in dev, server tests, and e2e without a separate seed step. `role: AGENT` since there's no more specific role and it never gets an `Account`/credential (nothing ever signs in as it). Its `name` is `lib/ticket-analysis.ts`'s exported `AI_ASSISTANT_NAME` constant, not a second hardcoded `"AI Assistant"` string in `queue.ts` — that's also what `evaluateAutoResolution` signs its own reply with (`signReply(reply, AI_ASSISTANT_NAME)`, same `signReply` `polishReply`/`generateReply` use), so the sent reply's sign-off name always matches the row it's attributed to. One side effect worth knowing: this row is real and non-deleted, so it appears in `GET /api/users` and `GET /api/users/assignable` like any other agent — a deliberately accepted minor consequence of reusing the existing `User`/`authorId` model rather than inventing a parallel one, not something worth its own schema carve-out yet.

If `evaluateAutoResolution` itself throws (or the reply/resolve `$transaction` does), `processAutoResolveTicketJobs`'s catch explicitly resets the ticket's `status` to `TicketStatus.OPEN` — not just logging and leaving whatever status it happened to already be in — so a failed AI call can never silently strand a ticket outside an agent's normal queue with no reply and no resolution. That reset runs in its own nested `try/catch`: a failure there is logged separately rather than allowed to propagate and fail the rest of the batch, preserving the same "one ticket's failure doesn't take down its neighbors" guarantee the outer per-job `try/catch` gives `processClassifyTicketJobs`/`processAutoResolveTicketJobs` generally.

`Ticket.resolvedByAi` (nullable-free `Boolean @default(false)`) is what actually distinguishes this from an agent manually resolving a ticket. `GET /api/tickets` excludes `resolvedByAi: true` tickets from its response **only when the caller didn't pass an explicit `status` filter** (`...(status ? {} : { resolvedByAi: false })` in its `where`) — the default (unfiltered) list view an agent normally works from shouldn't be cluttered with tickets nothing needs from them, but nothing here is actually hidden: filtering explicitly to `status=RESOLVED` (or any other status) returns them like any other ticket, since a caller who asked for that status meant it. `TicketsTable.tsx`'s Status column and `UpdateTicket.tsx`'s Status field both render a small `SparklesIcon` "AI"/"Resolved by AI" badge when `resolvedByAi` is true, so an agent who does go looking for one immediately knows it wasn't a colleague's work — the reply thread itself also naturally shows this, since the AI-authored reply's author name renders as "AI Assistant" like any other reply's author.

### Dashboard

`DashboardPage.tsx` — the `/` route, replacing what used to be a trivial API-health-check placeholder — is layout only (`UsersPage.tsx`/`TicketsPage.tsx`'s split), rendering `DashboardStats.tsx` for the actual content: five `Card`s (total tickets, open tickets, resolved-by-AI count, resolved-by-AI percent, average resolution time), each with a `lucide-react` icon and a big number. `DashboardStats.tsx` owns the `useQuery` and its `isPending`/`isError` states (a `Card` grid of `Skeleton`s, or `ErrorMessage`) — same shape as every other data-fetching component in this codebase.

**`GET /api/tickets/stats`** (`server/src/routes/tickets.ts`) is the endpoint behind it — `req.user`-only like every other ticket endpoint, no ADMIN gate. It's registered **before** `GET /api/tickets/:id`, not after: Express matches routes in registration order, and `/api/tickets/stats` also matches that route's `:id` param (it'd 400 as "Invalid ticket id" otherwise) — the literal path has to come first whenever a static segment could collide with an existing `:id` route. `totalTickets`/`openTickets`/`resolvedByAiCount` are three independent `prisma.ticket.count()` calls (no filter, `status: OPEN`, `resolvedByAi: true`), run via `Promise.all` alongside the resolution-time query below.

`resolvedByAiPercent` and `averageResolutionTimeMs` are computed by pure functions in `server/src/lib/ticket-stats.ts` (`computeResolvedByAiPercent`, `computeAverageResolutionTimeMs`) rather than inline in the route handler — deliberately, so the arithmetic can be unit-tested against fixed, made-up input (`ticket-stats.test.ts`) instead of asserting an exact number against the live, shared, constantly-mutating `helpdesk_test` database, which every other describe block in `tickets.test.ts` (and every other test file) also writes to. `tickets.test.ts`'s own `GET /api/tickets/stats` tests only check the route's wiring (auth, response shape, that `resolvedByAiPercent` is genuinely derived from the two counts in the same response, and that `totalTickets`/`openTickets` reflect a ticket created between two requests) — never an exact absolute value.

`averageResolutionTimeMs` is null, not `0`/`NaN`, when nothing has been resolved yet — "no data" and "resolved instantly" are different things the dashboard should render differently (`DashboardStats.tsx` renders `"—"` for `null` rather than calling `formatDuration(null)`). It's computed from `Ticket.resolvedAt` (new nullable column), **not** `updatedAt` — `updatedAt` gets bumped by a reply, a reassignment, or a category change (see the reply/assign handlers above), so it can't reliably mean "when this ticket was resolved." `resolvedAt` is set the first time a ticket leaves `OPEN`: `PATCH /api/tickets/:id` sets it to `now` when `status` changes and the ticket's previous status was `OPEN`, clears it back to `null` if the new status is `OPEN` (reopening), and leaves it untouched when moving between two non-`OPEN` statuses (e.g. `RESOLVED` -> `CLOSED` keeps the original resolution time rather than resetting the clock) or when only `category` changes. `lib/queue.ts`'s auto-resolve job sets it the same way (`resolvedAt: now` alongside `status: RESOLVED`, `resolvedByAi: true`, in the same `$transaction`) — a ticket judged auto-resolvable is always still `OPEN` at that point, so there's no reopened/already-non-open case to handle there.
